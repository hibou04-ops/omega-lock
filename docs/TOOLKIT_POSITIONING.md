# Toolkit Positioning

Omega-Lock is positioned as a measurement-grade optimization audit / release
gate. It is not a universal optimizer, not a dashboard, and not a replacement
for domain validation.

This document explains where it fits next to adjacent tooling without claiming
ecosystem rank, adoption, or superiority.

## Primary Role

Omega-Lock sits after candidate generation. A search method may propose a tuned
candidate; Omega-Lock asks whether the candidate survives local audit gates:

- declared hard constraints
- feasible candidate selection
- walk-forward or holdout evidence when configured
- append-only audit trail review
- optional hash-chain verification
- schema and artifact checks
- deterministic offline release hygiene

The intended use is release gating for calibration candidates whose failure
mode is not "the search did not run" but "the raw winner should not be trusted
without audit evidence."

## Relationship To Optimizers

Omega-Lock can run local search paths, but its positioning is audit-oriented.
The core distinction is:

| Tool role | Main question |
| --- | --- |
| Optimizer | Which candidate scores high under this objective? |
| Omega-Lock audit gate | Which candidate survives the declared evidence gates? |

Use Omega-Lock when the acceptance decision depends on constraints, audit
trail, train/test transfer, and reproducible artifacts. Do not use it as a
claim that a search method found a global optimum.

## When To Use Omega-Lock

Use Omega-Lock when these conditions hold:

- candidates are generated by tuning, search, or calibration
- the objective can be evaluated deterministically or with controlled seeds
- hard constraints can be stated as predicates over `(params, EvalResult)`
- reviewers need `best_any` and `best_feasible` separated
- a train/test or holdout gate is meaningful for the target
- an audit artifact is needed for CI, review, or release readiness

## When Not To Use Omega-Lock

Do not use Omega-Lock when:

- there is no measurable objective or parameter space
- the decision is qualitative and cannot be expressed as local evaluation data
- the target depends on live provider behavior that cannot be stabilized for CI
- the main need is a production runtime wrapper, UI, dashboard, or monitoring
  surface
- the requirement is cryptographic signing, immutable storage, or formal
  verification
- a direct unit test or static check would answer the question with less
  process

## When It Is Overengineering

Omega-Lock is probably too much process for:

- a one-off toy script with no release decision
- a deterministic formula where the correct answer can be proven directly
- a tiny parameter choice that can be reviewed by inspection
- a project that has no audit consumer for JSON artifacts
- a workflow where constraint failure has no practical consequence

In those cases, prefer a small deterministic test, a fixture, or a simpler
script.

## CI And Release Hygiene

Omega-Lock fits CI as an offline audit and drift-prevention layer. Default CI
should prefer deterministic local checks:

- `python scripts/check_repo_consistency.py --check`
- `python scripts/generate_readme_claims.py --check`
- `python scripts/run_golden_audit_cases.py --check`
- `python examples/demo_replay.py --check`
- `python examples/demo_sram.py --check`
- `python -m pytest -q`
- `python -m pyright src tests`
- `python -m ruff check src tests`

Release hygiene is separated from publishing:

- [scripts/publish_readiness.py](../scripts/publish_readiness.py) aggregates
  non-publishing local checks.
- [scripts/release_audit.py](../scripts/release_audit.py) audits local release
  surfaces.
- [scripts/wheel_smoke_install.py](../scripts/wheel_smoke_install.py) builds
  and installs a local wheel without PyPI.
- [scripts/post_release_verify.py](../scripts/post_release_verify.py) performs
  explicit post-release PyPI checks when network access is intentionally used.

`TOOLING_MISSING` and `ENVIRONMENT_BLOCKED` are blockers for release approval,
not success states.
